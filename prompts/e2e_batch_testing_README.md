## Architecture at a glance

```
CA ESP                                  Valdo E2E harness                          Oracle
------                                  -----------------                          ------
drops trigger sidecar  -->  valdo_watch_wrapper.sh
                                |
                                +--> run_e2e_source.sh (one per source)
                                       |
                                       +--> [optional] java_scripts.load (shell-out)
                                       +--> valdo run-etl-pipeline (file_to_staging)
                                       +--> [optional] java_scripts.generate (shell-out)
                                       +--> valdo run-etl-pipeline (L1, L2*, L3)
                                       +--> AUDIT.VALDO_RUN_FAILURES (one row per failed step)
                                       +--> report_root/index.html (per-source roll-up)
                                       +--> logs/e2e_{run_id}_{source}.jsonl
                                |
                                +--> [fan-out] run_e2e_all.sh -> build_rollup_index.py
                                                                  -> report_root/index.html (global)
                                                                  -> report_root/summary.json

* Output truth is covered by L2b (SQL truth) + L3 (baseline). The former
  `L2_regeneration` gate was retired (ADR 0012).
```

Gates per source. Two are Valdo-runnable output gates (`L1_structural`,
`L3_baseline_diff`), `L2b_sql_truth` is orchestrator-driven against Oracle, and
the Java load/generate steps are shelled out:

| Gate                | Run by               | Default blocking | Layer | Description |
|---------------------|----------------------|------------------|-------|-------------|
| `load_step`         | Java shell-out       | yes              |       | Java load script |
| `file_to_staging`   | `valdo db_compare`   | yes              |       | input file vs staging |
| `generate_step`     | Java shell-out       | yes              |       | Java generate script |
| `L1_structural`     | `valdo validate`     | yes              | L1    | mapping + rules check |
| `L2b_sql_truth`     | orchestrator/db      | per source       | L2b   | output file vs Oracle SQL truth |
| `L3_baseline_diff`  | `valdo compare`      | no               | L3    | Java vs pinned baseline |

> `L2_regeneration` was retired in ADR 0012 (it was a permanently-skipped
> `TODO(valdo-gap)`; L2b + L3 cover the truth and regression axes). A future
> mapping-driven `valdo regenerate` capability is tracked as a backlog item.

Scripts (`scripts/`):

| Script                              | What it does |
|-------------------------------------|---------|

## Environments and credentials

Two environments are wired today: **`sit`** and **`ait`**. `prod` is out of
scope for this iteration but `paths.yml` is structured so a `prod` overlay
is a one-block addition, not a refactor.

Oracle credentials follow the **same convention as the rest of Valdo**
(`ORACLE_USER` / `ORACLE_PASSWORD` / `ORACLE_DSN`, loaded from `.env` via
`python-dotenv`). The harness reads them through one chokepoint —
`scripts/e2e_lib/secret_resolver.py` — so a future flip to HashiCorp Vault
is a one-adapter change. Switch envs by switching which `.env` is loaded
(see `scripts/env-switch.sh`).

If your site needs simultaneous SIT + AIT credentials in one process,
edit `config/e2e/paths.yml` to point `oracle_dsn_env` / `oracle_user_env`
/ `oracle_password_env` at per-env names like `ORACLE_DSN_SIT`.

## How CA ESP drops trigger files

CA ESP signals the harness by dropping a **trigger sidecar** under a
source's trigger directory:

```
<trigger_root>/<arbitrary_name>.trigger
```

`<trigger_root>` resolves from `paths.yml` per env per source. Example
for SIT / SRC_A: `/data/sit/SRC_A/triggers/`.

Inside the sidecar, **line 1** carries the **basename** of the data file
the trigger announces:

```
$ cat /data/sit/SRC_A/triggers/load_done_20260514.trigger
SRC_A_input_HEADER_20260514.dat
```

The basename must match one of the regex patterns in
`paths.yml > filename_patterns` so the watcher can classify it as
`(source, file_type, direction)`. Patterns are evaluated in declaration
order; first match wins.

After processing, the watcher renames the sidecar atomically:

* Matched + dispatched:   `<name>.trigger.processed`
* Could not classify:     `<name>.trigger.unmatched` (plus a `.reason` companion file)

Both renames are idempotent on re-runs. A sidecar that already carries
one of those suffixes is skipped on the next poll. Atomic `os.replace`
guarantees CA ESP never sees a half-renamed file.

## Trigger filename grammar

The default `filename_patterns` in `paths.yml`:

```yaml
filename_patterns:
  - name: standard_input
    pattern: '^(?P<source>[A-Z0-9_]+)_input_(?P<file_type>[A-Z0-9_]+)_\d{8}\.dat$'
    direction: input
  - name: standard_output
    pattern: '^(?P<source>[A-Z0-9_]+)_(?P<file_type>P327|P328|P329|P330|P331|P332)_\d{8}\.txt$'
    direction: output

trigger_file:
  suffix: ".trigger"
  data_file_line: 1
```

Hard requirements:

1. Each pattern declares **named groups** `(?P<source>...)` and
   `(?P<file_type>...)`. Patterns missing either group fail validation
   at load time.
2. `direction` must be `input` or `output`.
3. Both groups must align with the corresponding entries in
   `config/e2e/sources/<SOURCE>.yml > input_files` / `output_files`. The
   harness does not cross-validate names at watch time, but a mismatch
   surfaces immediately at the per-source run as "no matching glob".

Examples of legal filenames:

| Filename                                | Matches as |
|-----------------------------------------|------------|
| `SRC_A_input_HEADER_20260514.dat`       | source=`SRC_A`, file_type=`HEADER`, direction=`input` |
| `SRC_A_input_PARTY_20260514.dat`        | source=`SRC_A`, file_type=`PARTY`, direction=`input` |
| `SRC_A_P327_20260514.txt`               | source=`SRC_A`, file_type=`P327`, direction=`output` |
| `LEGACY_BATCH_20260514.zip`             | **no match** → sidecar quarantined as `.unmatched` |

## Running the harness

### One source on demand

```bash
bash scripts/run_e2e_source.sh \
    --env sit \
    --source SRC_A \
    --run-id "$(date -u +%Y%m%d_%H%M%S)"
```

Produces:

* 6 per-file HTML reports under `report_root/...`
* 1 per-source `index.html` linking all of them
* JSONL log at `logs/e2e_<run_id>_<source>.jsonl`
* Zero or more rows in `AUDIT.VALDO_RUN_FAILURES` (one per failed step)

Exit code: 0 = clean, 2 = blocking failure, 3 = infrastructure error.

### Every source in parallel

```bash
bash scripts/run_e2e_all.sh \
    --env sit \
    [--run-id 20260514_120000] \
    [--concurrency 4] \
    [--source SRC_A] [--source SRC_B] ...    # optional filter
    [--strict]                                # treat any failed gate as a fail
```

The fan-out:

* Enumerates `config/e2e/sources/*.yml`.
* Launches `run_e2e_source.sh` per source under bounded concurrency.
* Each per-source run uses isolated `work_root` + `report_root` +
  JSONL log keyed by `(run_id, source)` — parallel-safe by construction.
* When all jobs finish, invokes `build_rollup_index.py` to produce the
  global roll-up at `report_root/index.html` + `report_root/summary.json`.

### Trigger-file daemon mode

```bash
bash scripts/valdo_watch_wrapper.sh --env sit [--poll-interval 5]
```

Polls every per-source `trigger_root` every `--poll-interval` seconds
(default **5**), classifies new sidecars, deduplicates by source within
a cycle, and dispatches to `run_e2e_source.sh`. Worst-case latency from
sidecar drop to per-source run start is the poll interval (default 5s).

`SIGTERM` / `SIGINT` causes a graceful exit at the next poll boundary.
Run under systemd with `Restart=on-failure` or as a long-running CA
ESP job.

## How to add a new source (5-step checklist)

1. **Copy the SRC_A template:**

   ```bash
   cp config/e2e/sources/SRC_A.yml config/e2e/sources/SRC_<NEW>.yml
   ```

   Edit the new file: set `source:`, `release_tag:`, `java_scripts:`,
   `staging_tables:`, `input_files:` (≥ 5 per the design),
   `output_files:` (6 per the design), and per-gate `blocking` /
   `invoke_java` flags. The `tolerance.ignore_fields` list per output
   file is consumed by the L3 pre-processor (see
   [Known gaps](#known-gaps-vs-valdos-current-capabilities)).

2. **Ensure mappings and rules exist** at the paths you declared in
   `input_files[*].mapping`, `output_files[*].mapping`, and
   `output_files[*].rules`. If you bumped a mapping `version` field, the
   L3 gate will fail until you also promote a new baseline (step 5).

3. **Regenerate the pipeline YAML for both envs:**

   ```bash
   python scripts/generate_pipeline_yaml.py \
       --source SRC_<NEW> --env sit
   python scripts/generate_pipeline_yaml.py \
       --source SRC_<NEW> --env ait
   ```

   Commit the resulting `config/e2e/pipelines/<env>/SRC_<NEW>.pipeline.yaml`
   files. Use `--check` in CI to guarantee the committed YAML stays in
   sync with the source config.

4. **Smoke-test in SIT** with Java disabled and the failure sink off:

   ```bash
   VALDO_E2E_DISABLE_JAVA=1 \
   VALDO_E2E_DISABLE_FAILURE_SINK=1 \
     bash scripts/run_e2e_source.sh \
         --env sit --source SRC_<NEW> \
         --run-id "smoke_$(date -u +%Y%m%d_%H%M%S)"
   ```

   Inspect the per-source roll-up and the JSONL log. Once the L1
   gate passes against a real Java-generated output, proceed to step 5.

5. **Promote the first baseline** using a QA-signed-off run (see next
   section). Without a manifest entry the L3 gate will fail every time;
   add the new source's pin with the comment "initial pin for
   SRC_<NEW>".

## How to promote a baseline

When a mapping changes, or when a new source is added, the L3 baseline
must be refreshed **atomically with the mapping change**. Use:

```bash
bash scripts/promote_baseline.sh \
    --env sit --source SRC_A \
    --release-tag R2026.06 \
    --run-output-dir /data/sit/_reports/20260514_120000/SRC_A \
    --approved-by qa-lead@example.com \
    --comment "Refresh after mapping bump in MR !1234"
```

What this does:

1. For each `output_files[*]` in the source's YAML, locates the most
   recently modified Java-generated output under `--run-output-dir`
   matching `glob`.
2. Reads `version` (or `mapping_version`) from the mapping JSON; falls
   back to `"unversioned"` if absent.
3. Copies the file to
   `baselines/<env>/<source>/<release_tag>/<file_type>.txt`.
4. Appends a new entry to `baselines/manifest.json` recording
   `(env, source, file_type, release_tag, mapping_version,
   approved_by, approved_at, comment)`.

Safety nets:

* **Refuses to overwrite an existing baseline file** unless `--force`
  is supplied. This guarantees mapping_version and baseline change
  atomically.
* **Idempotent at the manifest layer**: re-running with the same
  `(env, source, file_type, mapping_version, release_tag)` tuple
  appends nothing.
* **Pre-write validation**: the post-mutation manifest is validated
  through `BaselineResolver.from_dict` before it lands on disk. A
  manifest that would fail to load is never written.

Useful flags:

* `--file-type P327 --file-type P328` — promote a subset.
* `--dry-run` — print the summary JSON; write nothing.
* `--force` — overwrite an existing baseline file (e.g. legitimate
  re-promotion after a botched first attempt; explain in the MR).

**CODEOWNERS owns this approval gate.** The `--approved-by` value is
recorded in the manifest, but the real review happens on the resulting
MR. Mapping owners review the manifest diff and the new baseline
file together.

## How to read the failure table

Every failed step in any gate produces one row in:

```sql
AUDIT.VALDO_RUN_FAILURES
```

DDL: `scripts/sql/audit_valdo_run_failures.sql`. The table is
**append-only** — no `UPDATE`, no `DELETE`. Duplicates are accepted by
design (retries must not poison the trail with `ORA-00001`).

Routine queries:

```sql
-- All failures from a specific run
SELECT failed_at, source, gate_name, layer, error_type, error_count,
       row_count, file_name, blocking
  FROM AUDIT.VALDO_RUN_FAILURES
 WHERE run_id = '20260514_120000'
 ORDER BY failed_at;

-- Last 24 hours of blocking failures across all sources in SIT
SELECT failed_at, source, gate_name, layer, file_name, error_count
  FROM AUDIT.VALDO_RUN_FAILURES
 WHERE env = 'sit'
   AND blocking = 1
   AND failed_at > SYSTIMESTAMP - INTERVAL '24' HOUR
 ORDER BY failed_at DESC;

-- Top 10 noisiest gates by failure count this week
SELECT source, gate_name, COUNT(*) AS failures
  FROM AUDIT.VALDO_RUN_FAILURES
 WHERE failed_at > SYSTIMESTAMP - INTERVAL '7' DAY
 GROUP BY source, gate_name
 ORDER BY failures DESC
 FETCH FIRST 10 ROWS ONLY;

-- Drill into one failure's payload
SELECT failure_detail
  FROM AUDIT.VALDO_RUN_FAILURES
 WHERE failure_id = 12345;   -- failure_detail is a JSON CLOB
```

Column reference:

| Column            | Meaning |
|-------------------|---------|
| `failure_id`      | identity PK |
| `run_id`          | matches the JSONL log filename suffix |
| `env`             | `sit` or `ait` |
| `source`          | the source identifier |
| `pipeline_name`   | name from the pipeline YAML (e.g. `e2e_sit_SRC_A`) |
| `gate_name`       | `file_to_staging` / `L1_structural` / `L2b_sql_truth` / `L3_baseline_diff` / `load_step` / `generate_step` |
| `gate_stage`      | `input` / `output` / `java` / NULL |
| `layer`           | `L1` / `L2` / `L3` / NULL |
| `file_name`       | basename of the failing file (when known) |
| `file_type`       | `HEADER` / `P327` / ... |
| `mapping_path`    | path to the mapping JSON in use |
| `mapping_version` | the `version` field from the mapping JSON |
| `error_type`      | `structural` / `compare_diff` / `threshold_breach` / `java_step_failed` / ... |
| `error_count`     | number of failed rows / messages |
| `row_count`       | total rows processed |
| `report_path`     | path to Valdo's per-file HTML report |
| `blocking`        | `1` if the gate halted the source, `0` if informational |
| `failed_at`       | UTC timestamp |
| `failure_detail`  | short JSON CLOB with step-level details |

## How to read the roll-up index

Two artifacts live at the **per-run reports root** (the parent of every
per-source report dir for one run):

* `index.html` — the global roll-up. Self-contained, no external
  assets, viewable from any browser or `rsync`-ed off the RHEL host.
  Sections:
  - **Totals** — sources scanned, gates passed/failed/skipped/infra-error,
    sources with blocking failure.
  - **Sources** — per-source counts and a link to that source's roll-up.
  - **Gates** — one row per gate per source with layer tag, blocking
    flag, step count, row/error counts, and a link to Valdo's per-file
    HTML report.
* `summary.json` — machine-readable mirror (`schema_version: 1`,
  stable shape) for downstream automation (Splunk, dashboards,
  notifier hooks).

Per-source artifacts (one level deeper, under `<reports_root>/<source>/`):

* `index.html` — per-source roll-up table.
* `summary.json` — per-source machine summary (the global roll-up
  aggregates these).
* `<file>.html` — Valdo's per-file HTML report, one per output file
  (untouched — the harness does not modify Valdo's report renderer).

To regenerate just the global roll-up after a partial run:

```bash
python scripts/build_rollup_index.py \
    --reports-dir /data/sit/_reports/20260514_120000 \
    [--strict]   # treat any failed gate as a fail, not just blocking ones
```

Exit codes mirror the per-source wrapper: 0 / 2 / 3.

## Behavior-affecting environment variables

All four are read by the wrappers in `scripts/`; none affect Valdo
internals.

| Env var                              | Default | Effect when `=1` |
|--------------------------------------|---------|------------------|
| `VALDO_E2E_DISABLE_JAVA`              | unset   | Skip Java `load_step` / `generate_step` shell-outs. Useful on dev / Windows. |
| `VALDO_E2E_DISABLE_FAILURE_SINK`      | unset   | Do not write to `AUDIT.VALDO_RUN_FAILURES`. Failures are still logged to JSONL. |
| `VALDO_E2E_DISABLE_L2B`               | unset   | Skip the L2b SQL-truth gate (e.g. Oracle unreachable in dev / CI). |
| `VALDO_PYTHON`                        | unset   | Override the Python interpreter the bash wrappers invoke (otherwise `python3` → `python`). |
| `SECRETS_PROVIDER`                    | `env`   | `env` (default) or `vault` (stub adapter — not yet implemented). |

## Exit codes

Every wrapper and every Python CLI in this harness uses the same scheme:

| Code | Meaning |
|------|---------|
| `0`  | All blocking gates passed (or no work to do, in `--once` mode). |
| `2`  | At least one **blocking** gate failed. |
| `3`  | Infrastructure error: DB unreachable, config invalid, missing baseline, etc. |

`build_rollup_index.py --strict` upgrades any non-blocking failure to
exit `2` — useful in CI guardrails where you want to ratchet zero-tolerance
on a per-output-file basis once a source is mature.

## Logs

Three log streams:

1. **Per-source JSONL** at `logs/e2e_{run_id}_{source}.jsonl`. One
   structured event per line:
   ```
   {"ts":"2026-05-14T12:00:01.123Z","level":"INFO","event":"gate_started",
    "run_id":"20260514_120000","env":"sit","source":"SRC_A","gate":"L1_structural"}
   ```
   Reserved keys (`ts`, `level`, `event`, `run_id`, `env`, `source`) are
   stamped from logger identity and cannot be spoofed by callers.
   Append-only, thread-safe, never raises on disk-full or permission errors.

2. **Watcher JSONL** at `logs/e2e_watch_{env}_{YYYYMMDD}.jsonl`. One
   file per env per UTC day. Records `source_run_started`,
   `source_run_finished`, `trigger_unmatched`, `trigger_rename_failed`.

3. **Oracle audit table** `AUDIT.VALDO_RUN_FAILURES` — see
   [How to read the failure table](#how-to-read-the-failure-table).

Standard tail / grep commands:

```bash
# Watch one source in real time during a run
tail -F logs/e2e_20260514_120000_SRC_A.jsonl | jq .

# Find every failed gate event for one run across all sources
grep '"event":"gate_failed"' logs/e2e_20260514_120000_*.jsonl | jq .

# Find every unmatched trigger today
grep '"event":"trigger_unmatched"' logs/e2e_watch_sit_$(date -u +%Y%m%d).jsonl | jq .
```

## Known gaps vs. Valdo's current capabilities

The prompt forbids modifying Valdo internals. Where Valdo lacks a
capability the harness needs, we deliver a **wrapper** that achieves
the behavior externally, marked with `TODO(valdo-gap)`. When the gap is
closed inside Valdo, swap in the native path and delete the wrapper.

| Gap                                  | Today's workaround                                         | Touch point |
|--------------------------------------|------------------------------------------------------------|-------------|
| `valdo compare` has no `--ignore-fields` flag | `scripts/e2e_lib/ignore_field_filter.py` blanks the configured fields in both files into a temp dir before invoking `valdo compare`. Fixed-width only today; delimited is out of scope for this iteration. | M5 §6(f) |
| No `valdo regenerate` CLI            | `L2_regeneration` was **retired** (ADR 0012) rather than carried as a permanent skip: the output-truth axis is covered by the L2b SQL-truth gate and the regression axis by L3. A future mapping-driven `valdo regenerate` capability is tracked as a backlog item (ADR 0012, Option A). | retired — see ADR 0012 |
| `valdo run-etl-pipeline` has no `--gate <name>` filter | `scripts/e2e_lib/split_pipeline.py` writes a trimmed pipeline YAML per phase under `work_root/pipelines/` before each `valdo run-etl-pipeline` call. | M4 |
| `valdo` has no `shell` step type     | The Java `load_step` and `generate_step` are invoked by the bash wrapper (`run_e2e_source.sh`), not by the pipeline YAML. The pipeline YAML omits these gates entirely. | M3 / M4 |
| Valdo's `watch` polls every 30s and routes to suites, not pipelines | `scripts/valdo_watch_wrapper.sh` provides a dedicated E2E watcher with a 5s default poll, routing through `PathResolver.classify_filename` to `run_e2e_source.sh`. | M7 |

No Valdo internal module was modified by this harness. `git diff` against
`src/` is empty by construction; CI is encouraged to enforce this with a
simple guardrail (`git diff --name-only | grep -q '^src/' && exit 1`).

## Troubleshooting

**The watcher dispatches nothing even though I dropped a sidecar.**

* Check the filename grammar: `python -m scripts.e2e_lib.watch --env sit --once` will rename the sidecar to `.unmatched` with a `.reason` companion. The reason is one of `empty_or_unreadable` or `no_pattern_matched`.
* Check `paths.yml > filename_patterns`: patterns are evaluated in order, first match wins. A new pattern that should match must come before any broader one that accidentally matches first.
* Check the per-source trigger dir resolution: `python -m scripts.e2e_lib.path_resolver` (not exposed yet — read `paths.yml > envs.<env>.trigger_root` directly).

**`run_e2e_source.sh` exits 3 with "pipeline_yaml_missing".**

You probably forgot to regenerate the pipeline YAML after editing the
source config. Run:
```bash
python scripts/generate_pipeline_yaml.py --source SRC_X --env sit
```
And commit the result.

**L3 fails with `BaselineResolverError: no baseline pinned for mapping_version=...`.**

A mapping was bumped without an accompanying baseline promotion. Either
revert the mapping change or run `scripts/promote_baseline.sh` (see
[How to promote a baseline](#how-to-promote-a-baseline)).

**`FailureSinkError: failed to connect to Oracle`.**

The wrapper degrades gracefully: failures are still recorded in JSONL.
If you want to suppress the Oracle attempt entirely (e.g. on dev), set
`VALDO_E2E_DISABLE_FAILURE_SINK=1`.

**A blocking gate failed but the run continued.**

It did not — re-read the per-source roll-up: Valdo halts on the first
blocking failure within a phase (M4 confirms `gate.blocking=true →
pipeline_failed → break`). Any "later" gate you see in the report ran
in an earlier or independent phase. The exit code is the source of
truth: `2` means a blocking gate failed.

**The global roll-up shows `sources_without_summary`.**
