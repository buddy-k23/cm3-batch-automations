Quick Start — 5 minutes to your first validation

Follow these six steps in order. Every command block has a Copy button in the corner; the gold $ prompt is decorative and is excluded from what gets copied. By the end you will have validated a sample file and opened the resulting HTML report.

1

Confirm Python 3.11 and clone the repo

Valdo targets Python 3.11 on RHEL 8.9+. Older 3.9/3.10 also work for local dev.

$python --version # expect Python 3.11.x $git clone <repo-url> $cd valdo
2

Create a virtualenv and install

Use the platform helper script — or do it by hand. Either approach installs Valdo in editable mode so the valdo CLI is on your PATH.

# Windows $powershell -ExecutionPolicy Bypass -File scripts/setup_windows.ps1 $.\.venv\Scripts\Activate.ps1 # macOS / Linux $bash scripts/setup_mac.sh # or setup_rhel.sh $source .venv/bin/activate
3

Configure environment secrets

Copy the sample .env and fill in the three mandatory keys. API_KEYS must be non-empty or every protected endpoint returns 503 (issue #9 fail-closed behaviour).

$cp .env.example .env # Edit .env — the four keys you almost always need: # API_KEYS=your-strong-random-key-here # ORACLE_USER=APP_INT # ORACLE_PASSWORD=<password> # ORACLE_DSN=<host>:1521/<service> # VALDO_SESSION_SIGNING_KEY=<random-32-bytes> # only if auth.enabled=true
4

Verify the install

valdo info prints version, Python, and Oracle connectivity. A green ✓ on the Oracle line means thin-mode is reachable.

$valdo --help $valdo info
5

Run your first validation

Validate the bundled customer sample against the bundled mapping. The HTML report opens metrics tiles, per-field details, and a download-errors button.

$valdo validate \ -f data/samples/customers.txt \ -m config/mappings/customer_mapping.json \ -o reports/my_first_run.html \ --detailed

tip Add --use-chunked --chunk-size 50000 for files over ~200 k rows.

6

Open the report — or start the web UI

Open the HTML file directly, or launch the FastAPI server and use the in-browser Quick Test tab. Default address: http://localhost:8000/ui.

# Option A — open the HTML report $start reports\my_first_run.html # Windows $open reports/my_first_run.html # macOS $xdg-open reports/my_first_run.html # Linux # Option B — start the Web UI $valdo serve --host 0.0.0.0 --port 8000 # then visit http://localhost:8000/ui

Overview

Valdo is an automated batch file validation, comparison, and ETL testing tool with multi-database support, a REST API, and a modern web UI. It is mapping-driven: layouts and rules are declared in JSON/YAML, never hardcoded. The same business logic backs both the valdo CLI and the FastAPI server, with chunked processing for large files and a multi-record umbrella for files that carry several record types in one batch.

KEY

✅ Validate

valdo validateSchema + rules + threshold check; emits HTML/JSON report.
valdo validate --multi-recordValidate a file with multiple record types using an umbrella YAML.
--strict-fixed-widthField-level format checks (basic / format / all depth via --strict-level).
--use-chunkedMemory-bounded streaming for 100k+ row files; pair with --chunk-size.
--export-errorsWrite only failed rows to a CSV for triage.
--suppress-pii / --no-suppress-piiToggle PII redaction in HTML reports (default: on).
# Basic validation with HTML report $valdo validate \ -f data/samples/customers.txt \ -m config/mappings/customer_mapping.json \ -o reports/customers.html --detailed # With rules + strict fixed-width + chunked $valdo validate \ -f data/incoming/p327_today.txt \ -m config/mappings/p327_mapping.json \ -r config/rules/p327_business_rules.json \ --use-chunked --chunk-size 50000 \ --strict-fixed-width --strict-level format \ --export-errors reports/p327_errors.csv \ -o reports/p327.html # Multi-record (SHAW ATOCTRAN umbrella) $valdo validate \ -f data/incoming/atoctran_shaw_today.txt \ --multi-record config/mappings/SHAW_ATOCTRAN.yaml \ -o reports/atoctran.html

🔁 Compare

valdo compareFile-to-file comparison with optional key columns + thresholds.
valdo db-compareExtract from Oracle (or PG/SQLite) and compare against a batch file.
--apply-transformsRun mapping transforms on DB rows before diff (db-compare only).
--thresholdsThreshold JSON file controlling pass/fail (max_errors, max_percent).
# File-to-file with key columns $valdo compare \ -f1 data/snapshot_yesterday.txt \ -f2 data/snapshot_today.txt \ -k customer_id \ --use-chunked --chunk-size 50000 \ -o reports/diff.html # DB-to-file with transforms applied $valdo db-compare \ -q 'SELECT * FROM CUSTOMER' \ -m config/mappings/customer_mapping.json \ -f data/customers_export.txt \ -k CUSTOMER_ID \ --apply-transforms \ --output-format html \ -o reports/db_vs_file.html

Recipes — How do I…?

Task-oriented playbooks for the things people actually ask. Each recipe lists the time it takes, the inputs you need on hand, the exact commands (with Copy buttons), and the relevant Web UI alternative. Recipes are independent — jump to the one that matches your problem.

1 · Validate a fixed-width file with business rules ~3 min

You have: a fixed-width batch file, a mapping JSON, and (optionally) a business rules JSON.

You want: an HTML report with errors highlighted, plus a CSV of failed rows for triage.

$valdo validate \ -f data/incoming/p327_today.txt \ -m config/mappings/p327_mapping.json \ -r config/rules/p327_business_rules.json \ --strict-fixed-width --strict-level format \ --export-errors reports/p327_errors.csv \ -o reports/p327.html \ --detailed

Web UI Quick Test tab → drop file → select mapping → tick "Suppress PII" → Validate. Drift badge + Download Errors button appear inline.

2 · Validate a multi-record file (SHAW ATOCTRAN / TRANERT) ~5 min

You have: a fixed-width file containing several record types in one batch; an umbrella YAML at config/mappings/SHAW_*.yaml declares the discriminator and per-type mappings.

You want: a report broken down by record type plus any cross-type rule violations (e.g. header trailer count).

# ATOCTRAN — 7 record types discriminated by TRANSACTION-CODE @ pos 25-27 $valdo validate \ -f data/incoming/atoctran_shaw_today.txt \ --multi-record config/mappings/SHAW_ATOCTRAN.yaml \ -o reports/atoctran.html # TRANERT — batch header + 6 detail types; header_trailer_count checked automatically $valdo validate \ -f data/incoming/tranert_shaw_today.txt \ --multi-record config/mappings/SHAW_TRANERT.yaml \ -o reports/tranert.html

Web UI Quick Test tab → upload the YAML in the "Multi-Record YAML" slot above Validate.

3 · Add a new source from scratch (BSA workflow) ~30 min

You have: a layout spec from the source team (Excel/PDF). For multi-record sources, you also have the discriminator field + position.

You want: a working mapping JSON, optional rules JSON, and (if multi-record) an umbrella YAML, all reconciled against the DB.

  1. Author mappings/csv/<source>/<source>_mapping.csv from the standard template.
  2. Author rules/csv/<source>/<source>_rules.csv if business rules apply.
  3. Convert both to JSON (strict mode flags any malformed row).
  4. Reconcile against the DB schema.
  5. Smoke-validate against a real sample.
  6. (Multi-record only) Author the umbrella YAML and validate again with --multi-record.
# 1+2 Author CSVs in mappings/csv/<source>/ and rules/csv/<source>/ # 3 Convert to JSON $./scripts/run_convert_mappings.sh mappings/csv config/mappings $./scripts/run_convert_rules.sh rules/csv config/rules # 4 Reconcile against the DB $valdo reconcile -m config/mappings/<source>_mapping.json # 5 Smoke-validate $valdo validate \ -f data/samples/<source>_sample.txt \ -m config/mappings/<source>_mapping.json \ -r config/rules/<source>_rules.json \ -o reports/<source>_smoke.html # 6 (Multi-record only) author umbrella YAML, then: $valdo validate \ -f data/samples/<source>_sample.txt \ --multi-record config/mappings/<source>.yaml \ -o reports/<source>_multi_smoke.html

Web UI Mapping Generator tab will do steps 1–3 + the umbrella from Excel. Multi-Record Wizard handles step 6 interactively.

4 · Compare a database table against a batch file ~5 min

You have: Oracle credentials in .env and a batch file you suspect drifted from the table.

You want: a field-level diff report keyed by primary key.

# By bare table name $valdo db-compare \ -q CUSTOMER \ -m config/mappings/customer_mapping.json \ -f data/customers_export.txt \ -k CUSTOMER_ID \ --apply-transforms \ --output-format html \ -o reports/db_vs_file.html # By SQL — apply WHERE filters or joins as needed $valdo db-compare \ -q "SELECT customer_id, first_name, last_name, status FROM CUSTOMER WHERE status='ACTIVE'" \ -m config/mappings/customer_mapping.json \ -f data/active_customers.txt \ -k customer_id \ -o reports/active_diff.html

Web UI DB Compare tab → pick a named connection from config/db_connections.yaml → paste SQL or table name → upload the file → Run.

5 · Wire Valdo into CI as a build gate ~15 min

You have: a CI runner (GitLab / GitHub / Azure) and a need to fail builds on validation regressions.

You want: a non-zero exit on threshold breach so the pipeline stops; a JSON report for the build artefact.

# Single command — exits 1 on validation errors $valdo validate \ -f data/incoming/$BATCH_FILE \ -m config/mappings/$MAPPING.json \ -r config/rules/$RULES.json \ -o reports/validation.json # .json = machine-readable # Pipeline gate — exits 2 on any blocking gate failure $valdo run-etl-pipeline \ --config config/pipelines/nightly_etl.yaml \ --run-date $RUN_DATE \ --output reports/pipeline_run.json # Drift gate — exits 1 when reconcile finds new errors vs baseline $valdo reconcile-all \ -d config/mappings \ -o reports/reconcile_today.json \ --baseline reports/reconcile_baseline.json \ --fail-on-drift

Templates GitHub Actions composite + Azure step template + GitLab job in ci/ + azure-pipelines-ci.yml. Exit codes: 0 success · 1 soft-fail · 2 blocking · 3 infra.

6 · Process a very large file (100k+ rows) without blowing memory ~2 min to configure

You have: a file that's too big to fit comfortably in RAM as a single DataFrame.

You want: bounded memory + parallel cores + a progress bar.

# Validate, chunked + parallel $valdo validate \ -f data/incoming/p327_2M_rows.txt \ -m config/mappings/p327_mapping.json \ --use-chunked --chunk-size 50000 --workers 3 \ --strict-fixed-width --strict-level format \ --progress \ -o reports/p327_big.html # Compare requires keys when chunked $valdo compare \ -f1 data/yesterday.txt -f2 data/today.txt \ -k customer_id \ --use-chunked --chunk-size 50000 \ -o reports/diff_big.html

guidance Default chunk size is 100k; drop to 50k on memory-constrained hosts. Start with --workers 1, raise to cores − 1. See docs/CHUNKED_PROCESSING.md.

7 · Produce a PII-safe sample from a production file ~3 min

You have: a production file with sensitive fields you want to share with the dev team.

You want: a file that preserves layout and key relationships but contains no real PII.

Six strategies available per field: preserve, preserve_format, deterministic_hash, random_range, redact, fake_name. Output is length-safe for fixed-width.

# masking rules JSON declares strategy per field # { # "fields": { # "SSN": {"strategy": "deterministic_hash"}, # "FIRST_NAME": {"strategy": "fake_name"}, # "ACCOUNT_NUMBER": {"strategy": "preserve_format"}, # "PHONE": {"strategy": "random_range"}, # "INTERNAL_NOTES": {"strategy": "redact"} # } # } $valdo mask \ -f data/prod/customer_today.txt \ -m config/mappings/customer_mapping.json \ -r config/masking/customer_masking.json \ -o data/safe/customer_safe.txt

tip deterministic_hash gives the same input the same output every run, so joins across masked tables still work.

8 · Auto-run a suite when a batch file arrives ~5 min

You have: an upstream scheduler (CA ESP, cron, etc.) that drops a .trigger sidecar when a batch file is ready.

You want: a daemon that watches the directory, classifies the trigger, runs the matching YAML suite, and renames the sidecar atomically.

$valdo watch \ --dir /data/triggers \ --suites config/test_suites \ --env sit \ --output-dir reports \ --interval 30 # Trigger sidecar example: # /data/triggers/load_done_20260514.trigger # line 1: SRC_A_input_HEADER_20260514.dat

harness alt For SIT/AIT batch use the E2E wrapper at scripts/valdo_watch_wrapper.sh (5s default poll, classifies via paths.yml filename patterns).

9 · Catch schema drift before production breaks ~5 min

You have: a directory of mapping JSONs that must stay in sync with the live DB schema.

You want: a CI job that detects new errors/warnings since a known-good baseline and fails the build.

# 1 Capture a baseline once after a clean reconcile $valdo reconcile-all -d config/mappings -o reports/reconcile_baseline.json $git add reports/reconcile_baseline.json && git commit -m 'pin reconcile baseline' # 2 In CI, run reconcile-all against the baseline $valdo reconcile-all \ -d config/mappings \ -o reports/reconcile_today.json \ --baseline reports/reconcile_baseline.json \ --fail-on-drift # 3 Drift on a single file? Use detect-drift for fast feedback $valdo detect-drift -f data/incoming/p327_today.txt -m P327_SHAW_M06

Web UI Quick Test surfaces a Drift Badge with the changed fields when the validated file's layout diverges from its mapping.

10 · Enable LDAPS login for the Web UI ~10 min

You have: a corporate LDAPS server, a CA bundle, and a need to log users in by AD username rather than handing out API keys.

You want: users hit /ui, are redirected to /auth/login, log in with corporate creds, and get a signed session cookie. Service callers keep using X-API-Key.

Every flow path through the system terminates at the unified reports layer or at AUDIT.VALDO_RUN_FAILURES. Source: docs/architecture.md.

E2E harness gates design — L2b not yet implemented

Per-source output validation in the E2E harness runs as a chain of independently-blocking gates. The Valdo-runnable output gates are L1_structural and L3_baseline_diff; the orchestrator-driven L2b SQL-Truth gate covers the output-truth axis for SHAW TRANERT. The former L2_regeneration gate was retired (ADR 0012). Source: scripts/e2e_lib/run_source.py + the TRANERT design session (docs/handover/TRANERT_DB_TESTING_SESSION_SUMMARY.md).

L1 Structural wired
valdo validate against the umbrella + per-record-type mappings. Catches field width, format, not_null, in_list on every field, including ones whose value is computed by complex Java logic upstream. Blocking on every source.
config/mappings/SHAW_TRANERT.yaml + per-type JSONs
L2 Regeneration retired
Retired (ADR 0012). It was a permanently-skipped TODO(valdo-gap); the output-truth axis is now covered by the L2b SQL-truth gate and regression by L3 baseline. A future mapping-driven valdo regenerate capability is tracked as a backlog item (ADR 0012, Option A).
retired · ADR 0012
L2b SQL-Truth designed
Reconciles the generated file against the same Oracle staging the Java reads from. Generic engine (scripts/e2e_lib/db_truth_comparator.py, planned) drives per-source declarative specs at config/e2e/sources/<SOURCE>/reconciliation/<file_type>.yml. All business logic lives in versioned .sql files (per-record-type expected views built with CREATE OR REPLACE); no Python per source. Idempotent bootstrap (no Alembic): every run re-creates views and reloads lookup CSVs from zero, so SIT and AIT cannot drift. First target: SHAW TRANERT (6 detail record types + batch header).
config/e2e/sources/SHAW/sql/tranert/ · scripts/e2e_lib/sql_bootstrap.py (planned)
L3 Baseline Diff wired
valdo compare of the new Java output against a signed-off golden baseline keyed by (ACCT_NUM, TRN-COD-ERT) for TRANERT. Catches any regression across all fields run-over-run, including those L2b chooses not to assert. Blocking; fails every run until the first baseline is promoted.
baselines/ · scripts/e2e_lib/baseline_resolver.py
DESIGN NOTE
L2b adoption is opt-in per source: a source becomes covered when (a) its reconciliation YAML lands under config/e2e/sources/<SOURCE>/reconciliation/ and (b) its SQL artifacts are checked in under the same path. Sources without those artifacts simply skip L2b, same shape as L2_regeneration today. The service account used by the harness already has DDL + temp-table privileges in SIT and AIT, which the idempotent bootstrap requires.

Design principles

Mapping-driven
No hardcoded file layouts. New sources are added by checking in JSON/YAML under config/ — no src/ change required.
CLI / API parity (ADR 0001)
commands/ and api/routers/ are wrappers; canonical logic lives in services/ so the two surfaces cannot drift.
Fail-fast exit codes
CI-friendly: non-zero on threshold breach, drift, or missing baseline. 3 reserved for infrastructure errors.
Chunked & memory-safe
--use-chunked path keeps RSS bounded for 100k+ row files (ADR 0002 + docs/CHUNKED_PROCESSING.md).
Fail-closed on secrets
Missing API_KEYS → 503; missing LDAP signing key → RuntimeError on startup; no implicit "open mode".
Human + machine output
Every command emits both an HTML report for operators and a JSON summary for automation. Audit logs are Splunk-compatible JSONL.

Authentication / Security

Valdo enforces two authentication modes that coexist on the same endpoints: X-API-Key for service-to-service callers (mandatory, fail-closed) and an optional LDAPS session cookie for interactive users. Network exposure is hardened by an IP-whitelist middleware, an SSRF guard on user-supplied URLs, an explicit trusted-proxies list, and PEM-bundle-validated TLS. The hardening is tracked under in-repo issues #9 (auth) and #10 (network/SSRF).

Hardening controls (issues #9 & #10)

Filter-injection guard RFC 4515
_escape_ldap_filter() sanitises the username before any LDAP filter interpolation, preventing injection through crafted usernames.
src/api/auth_ldap.py
TLS-only LDAP
The binder refuses any URI that does not start with ldaps://. ssl.CERT_REQUIRED validates the LDAP server certificate against auth.ldap.ca_cert_path.
Open-redirect guard
_safe_next() only accepts same-site relative paths starting with / (and not //); arbitrary ?next= values are dropped.
Generic credential errors
Bad username and bad password both return "Invalid credentials" — no user enumeration through error wording or timing.
Path-traversal containment 12 sites
Every upload & template-download endpoint resolves the path with Path.resolve() and asserts containment under the configured root via relative_to. Symlink escapes are rejected with HTTP 400.
GET /api/v1/templates/{filename}
IP whitelist middleware
When security.ip_whitelist is non-empty, only listed IPs/CIDRs are allowed. With trust_proxy: true the middleware walks X-Forwarded-For right-to-left, skipping addresses in security.trusted_proxies — fixes a previous "first IP wins" spoof.

SSRF guard URL validator
Scheme allowlist + IP-range blocks for any user-supplied URL. security.callback_allowlist in config/ui.yml can further restrict webhook callbacks to a fixed hostname list.
src/api/security/url_validator.py

SQL Reconciliation Gate (L2b) — how it works

The L2b SQL-Truth gate reconciles a Java-generated output file row-by-row, field-by-field against a SQL "truth" derived from the same Oracle staging data the Java batch reads. Unlike L1 (structural) and L3 (golden-baseline diff), L2b catches a Java mapping that drifts from the spec even when the file is structurally valid and matches yesterday's baseline. All business logic lives in versioned .sql + a per-source YAML manifest, so BAs and DBAs review it independently of the harness. First wired for SHAW TRANERT (issues #17–#19, #22).

WHY L2b
L1 proves the file is well-formed; L3 proves it matches a pinned baseline. Neither catches a Java code change that diverges from the mapping spec while still producing a valid file that happens to equal a stale baseline. L2b re-derives the expected values from current staging every run, so SIT/AIT cannot silently drift.

Where this gate sits — the full E2E gate chain

A single source runs as a chain of independently-blocking gates driven by scripts/e2e_lib/run_source.py. The input phase loads the file into Oracle staging; the output phase runs the Valdo ETL-pipeline gates; then the orchestrator runs L2b on top. A run exits 0 only if every blocking gate passed (2 on a blocking failure, 3 on an infrastructure error). Non-blocking gates record findings but never fail the run.

Gates 2–4 are emitted into a per-source pipeline YAML and run by valdo run-etl-pipeline; L2b_sql_truth is orchestrator-driven (like the Java shell-outs) and intentionally excluded from that YAML, so it runs after the output-phase gates. A source with no reconciliation YAML records l2b_not_configured and L2b stays non-blocking for it.

Running it end-to-end

On a RHEL host the thin bash wrappers delegate to the Python orchestrator. Run one source or fan out across all sources (the latter also builds the global roll-up). Findings for any failed gate are appended to AUDIT.VALDO_RUN_FAILURES; a per-source roll-up HTML is written under the report root.

# One source, full gate chain (input -> L1/L2/L3 -> L2b) $bash scripts/run_e2e_source.sh --env sit --source SHAW --run-id "$(date -u +%Y%m%d_%H%M%S)" # All sources in parallel, then build the global roll-up $bash scripts/run_e2e_all.sh --env sit --concurrency 4 # Dev/CI without Oracle: skip the SQL-reconciliation gate $VALDO_E2E_DISABLE_L2B=1 bash scripts/run_e2e_source.sh --env sit --source SHAW --run-id local # Treat ANY failed gate (not just blocking) as a failure $bash scripts/run_e2e_all.sh --env sit --strict

Exit codes (both wrappers): 0 all blocking gates passed · 2 a blocking gate failed · 3 infrastructure error. Useful env toggles: VALDO_E2E_DISABLE_JAVA=1 (skip Java load/generate), VALDO_E2E_ENABLE_L2=1 (enable the L2 regeneration gate), VALDO_E2E_DISABLE_FAILURE_SINK=1 (log only, no Oracle writes).

The four-step pipeline (per run, per output file)

The orchestrator (scripts/e2e_lib/run_source.py) runs L2b after the output-phase Valdo gates, but only for sources that ship a reconciliation YAML. Everything is idempotent — no persistent state between runs.

1

Bootstrap the SQL truth

Run 00_bootstrap/ — create-if-absent the app_int-owned helper tables and lookup tables (idempotent PL/SQL trapping ORA-00955). app_int holds CREATE TABLE but not CREATE VIEW, so the helpers are materialized as CTAS tables, not views (session-7 "shape B").

2

Refresh lookups + expected tables

Run 10_load/ — extract_tranert_properties.py regenerates the lookup CSVs if the Spring property-file SHA changed, then MERGE/TRUNCATE+INSERT reloads the lookup tables and re-populates the EXPECTED_*_TBL tables from the live driver.

3

Parse the output file

The multi-record parser dispatches each line to its record type via the umbrella discriminator (TRN-COD-ERT at pos 170, Batch Header by position "first"), then slices each line into per-field values using the per-record-type mapping JSON.

4

Reconcile & record

db_truth_comparator.reconcile() indexes the expected rows and file rows by each record type's key, compares field-by-field, and emits one FailureRecord per discrepancy into AUDIT.VALDO_RUN_FAILURES. A clean file produces zero violations and the gate passes.

Comparison model & violation kinds

For each record type the engine indexes both sides by the spec key and compares. Because the file key uses dash names (LN-NUM-ERT) and the SQL columns use underscores (LN_NUM_ERT), the expected SQL aliases the key column to the dash form via a quoted identifier so the same key resolves on both sides. It collects every discrepancy rather than failing fast:

Violation kindMeaning
field_mismatchFile value ≠ expected value for a reconciled field.
cardinality_violationFile row count for a key disagrees with the record type's cardinality.
missing_expectedAn expected (SQL) key has no matching file row.
unexpected_file_rowA file key has no matching expected row.
assertion_failedA cross-type assertion (e.g. header count) did not hold.
unknown_record_typeA file line's discriminator matched no configured record type.
KEY INSIGHT
The engine does strict trimmed-string equality — no numeric tolerance, no date parsing. So the expected SQL must emit values in the file's exact representation. SQL returns typed Oracle values (DATE, NUMBER); the file is fixed-width text. Aligning the two in SQL (not in the engine) keeps the comparator generic and the business logic reviewable.

Adapting L2b to other file types

The engine is file-type agnostic. It only knows "record types, each with a key, a cardinality, an expected rowset, and a field map." Whether a file carries one record type or twelve, the same db_truth_comparator drives it — you add a YAML + SQL, never Python. The only thing that changes is how many record types the umbrella declares and how rows are dispatched.

Aspect Single-transaction file (e.g. P327) Multi-transaction file (e.g. TRANERT)
Record types One logical type for the whole file (plus an optional header/trailer). Many — one per discriminator value, plus a positional header/trailer.
Dispatch No discriminator needed — every data line is the same type. Discriminator field at a fixed position routes each line (e.g. TRN-COD-ERT); header/trailer matched by position: first|last.
Umbrella mapping A single-entry umbrella (or a flat mapping JSON) pointing at one record layout. A .yaml umbrella listing every record type and its mapping JSON.
Expected SQL One expected_<type>.sql over one expected table. One expected_<code>.sql per record type.
Reconciliation YAML record_types: has a single entry. record_types: has one entry per umbrella type, keyed by the umbrella name.
Cross-type assertion Usually none (or a trailer record-count check). e.g. header.ITM-CNT-BRT == sum(detail_row_counts).
SINGLE-RECORD
For a flat, single-transaction file you simply declare one record type in the reconciliation YAML. Pick a stable business key (e.g. the account or transaction id), set cardinality: one_per_driver_row, point expected_sql at a SELECT over your expected table, and map each file field to its expected column. No discriminator, no positional header rules required — the engine indexes both sides by the key and diffs field-by-field exactly as it does for TRANERT, just with a single bucket.
MULTI-RECORD
For a multi-transaction file, the umbrella's discriminator does the routing and each record type gets its own entry. Use many_per_driver_row with a composite key when one driver row produces several detail rows (TRANERT 32005 is keyed (LN-NUM-ERT, CONTACT-ID)), zero_or_one_per_driver_row with a predicate for conditionally-emitted records (32010 only when CHG_OFF_CD='1'), and one_per_driver_row for the rest. A header/trailer is just another record type matched by position.

The portable recipe (any file type)

1

Describe the file

Author (or reuse) the umbrella + per-record-type mapping JSON so the parser can slice each line into named fields. One record type for single-transaction files; one per discriminator value for multi-transaction files.

2

Build the SQL truth

Write the bootstrap/load/expected SQL that materializes the expected rows from staging — one expected_*.sql per record type, each formatted to the file's representation (dates, padding, decimal scale) so strict-string equality holds.

3

Write the reconciliation YAML

For each record type: expected_sql, cardinality, key, and the file_field → expected_column map. Add any cross-type assertions (e.g. header/trailer counts). Park stateful-Java fields in ignored_fields.

4

Enable the gate

Set L2b_sql_truth: { blocking: true, invoke_java: false } in the source config. The orchestrator picks it up automatically; sources without a YAML stay non-blocking and record l2b_not_configured.

WHAT NEVER CHANGES
The comparator engine, the failure sink, the rollup, and the orchestrator wiring are shared and untouched across file types. Onboarding a new single- or multi-transaction file is entirely a config + SQL exercise — no src/ changes, in line with the project's hard rules.
